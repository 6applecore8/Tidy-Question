## 第 3 题：从架构上来讲 Agent 有几层？

**短答案：没有统一规定必须有几层。** 为了讲清楚职责，可以用下面的六层作为分析框架；这是学习时的划分，不是所有产品的官方标准。

```text
用户 / IDE / API
        ↓
入口交互层：接收问题、展示进度和结果
        ↓
规划与编排层：判断步骤、选择工具、决定是否委派
        ↓
模型层：理解上下文，生成建议、代码或工具调用
        ↓
工具执行层：读写文件、搜索、运行测试和命令
        ↓
环境与数据层：代码仓库、数据库、沙箱、外部服务

横跨各层：上下文与状态管理、权限安全、日志和测试
```

| 层 | 简单理解 | Coding Agent 例子 |
| --- | --- | --- |
| 入口交互层 | 跟用户沟通 | 接收“修复登录失败”，展示进度 |
| 规划与编排层 | 安排怎么干 | 先定位问题，再修改，最后运行测试 |
| 模型层 | 理解和生成 | 根据代码提出修改方案或工具调用 |
| 工具执行层 | 实际动手 | 搜索文件、修改代码、执行测试 |
| 环境与数据层 | 工作场地和资料 | Git 仓库、文件系统、数据库、隔离环境 |
| 横向支撑能力 | 给各层提供保障 | 保存上下文、控制权限、记录日志 |

**注意：**图中并不是所有请求都只能从上往下走一遍。Agent 往往是一个循环：模型提出工具调用 → 程序校验并执行 → 工具结果返回模型 → 决定下一步。另外，上下文管理和安全是跨多层的能力，把它们单独算成一层还是多层，取决于你怎么划分。

### 面试中怎么回答？

> 我一般按职责把 Coding Agent 分为交互入口、规划编排、模型、工具执行和运行环境几部分，同时把上下文管理、安全权限和日志观测作为横向能力。具体层数不是固定的，核心是区分谁负责理解和决策、谁真正执行操作，以及如何管理状态和安全边界。

## 第 6 题：Claude Code Coordinator 协调者模式的设计初衷是什么？

**短答案：让一个主 Agent 负责把握整体任务，把适合拆分的工作交给其他 Agent，再汇总结果。** 这样可以让子任务并行处理，同时减少所有细节挤在同一个上下文里的问题。

例如要排查 TidyQuestion 的启动问题：

```text
用户：帮我排查后端启动失败
             ↓
主 Agent：确定目标、拆分并安排检查
       ┌─────┼─────┐
       ↓     ↓     ↓
    检查配置  检查代码  检查启动日志
       └─────┼─────┘
             ↓
主 Agent 汇总证据，判断原因和下一步
```

这是说明性的例子，不表示 TidyQuestion 已经实现这些 Agent。

协调者模式想解决的实际问题主要有：

1. **任务拆分：**把大任务分成边界较清晰的小任务。
2. **并行和专长：**互不依赖的检查可并行，工作者也可以有不同专长。
3. **上下文分离：**子 Agent 在各自上下文里处理细节，再把必要结果反馈给主 Agent。
4. **统一交付：**主 Agent 对照用户目标汇总结果，检查冲突和遗漏。

这样做并不一定更快或更省钱：多 Agent 会增加通信、等待、合并和模型调用成本；多个 Agent 修改同一文件也可能冲突。简单任务可能单 Agent 更合适。

### 不要把 Claude 的各种功能混为一谈

Claude Code 的**子 Agent**可由主 Agent 委派，并向主 Agent 汇报；**Agent teams** 则允许成员通过共享任务和相互消息协作。因此，不能说“Claude Code 的多 Agent 都只能通过中心节点通信”。Claude 平台的 Managed Agents 文档也有独立的 coordinator 编排能力，不应把它的具体实现直接当成 Claude Code 所有模式的实现。

### 面试中怎么回答？

> 协调者模式的目的是把复杂目标的整体把控和子任务执行分开：主 Agent 分配适合独立处理的工作，子 Agent 使用各自的上下文完成任务并返回结果，主 Agent 再整合和验证。它适合有多个边界清晰子任务的场景，但会增加协调成本，也要处理文件冲突和上下文遗漏。
